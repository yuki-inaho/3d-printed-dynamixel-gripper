# テスト実行時間のプロファイルと改善記録

2026-09-25。i7-9750H（6コア/12スレッド、23 GB）。判定の対象と閾値は変えていない。

## 1. 計測の方法

- 全テストを `pytest -n 6 --durations=0` で計測し、準備処理（setup）と本体（call）をモジュール別に集計した。
- STEP 解析や距離計算は C++（OCCT）内部で時間を使うため、cProfile には現れない。
- そこで `cq.Shape.distance`・`intersect`・`cut`・`isValid` などを計時用に差し込み、呼び出し回数と時間を分解した。

## 2. 変更前の内訳（6並列、実時間334秒、テスト時間の合計1,338秒）

| 原因 | 規模 | 証跡 |
|---|---|---|
| 同じ35 MBの全腕 STEP を約15モジュールが個別に解析 | 1回17〜22秒、準備処理384秒の大半 | 解析10.3秒（競合なし）。同じ形状のバイナリ BREP 読み込みは0.33秒 |
| 連続クリアランス証明（`certify_interval`）の2分割で、中点が部分的に証明した範囲を捨てていた | guide_relief 片側127回、1回200〜370 ms | 一定0.3 mm のクリアランスで、証明済みの葉区間64個に対し、失敗した親区間が63個 |
| 距離計算のたびに固定側（フレーム・リンク）の準備処理をやり直していた | 1回244 ms → 再利用すると108 ms | 32姿勢で値の差0.0 |
| `installed_assembly()` が、捨てるカメラ組立を含めて Robonine の STEP を毎回2回解析 | 1回12.2秒のうち約11秒 | `donor_parts()` が5.5 MB の STEP を毎回解析 |
| 合成キャリブレーションの session fixture が、ワーカーごとに最大4回生成 | 1回約35秒 | `--dist loadfile` で4モジュールが別ワーカーに分散 |
| ファイル単位の振り分けで、guide_relief の1ファイル（約190秒）が1ワーカーに集中 | 実時間の下限を決めていた | 最長のファイルが1ワーカーで直列に実行される |

## 3. 変更点

1. **`scripts/step_cache.py`（`read_rows`）**
   - STEP の SHA-256、OCP/CadQuery のバージョン、形式番号をキーにした、バイナリ BREP のキャッシュ。
   - `tests/conftest.py` が `.pytest_cache` の下で有効にする。成果物を作るスクリプトの動作は変わらない。
   - メッシュは保存しない。BREP 本体の SHA-256 を照合し、壊れていれば STEP から作り直す。
   - xdist のワーカー間はファイルロックで排他し、書き込みは一時ファイルからの置き換えで行う。
   - 証拠の連鎖で依存ファイルとして記録されている `assembly_io.py` は変更していない。
2. **`certify_interval`**
   - 中点で証明できた範囲 ±(d−2ε)/L を除いた残りの区間だけを再検査する。
   - 根拠は従来と同じリプシッツ上界。検査回数は127 → 63回。
   - 健全性は、接触する負例と、ランダムな200関数の性質テストで確認した（`tests/test_certify_interval.py`）。
3. **`DistanceTo`**
   - `cq.Shape.distance` と同じ計算（BRepExtrema、既定のフラグ、マルチスレッド）で、固定側を1回だけ読み込む。
   - guide_relief と mechanism_insertion の距離証明に使う。
4. **pivot_motion**
   - 剛体変換で距離が変わらないことを使い、リンクの座標系で距離を測る。
   - これでリンクが静止し、`DistanceTo(リンク)` を全姿勢・全部品で使い回せる。
   - 実部品48組で、元の方式との差は最大2.8e−14 mm（回帰テストあり）。
5. **`camera_jig.build.donor_parts`** を `read_rows` にした。
   - `installed_assembly()` は12.2秒 → 2.2秒（キャッシュあり）。
6. **並列の振り分け（`tests/conftest.py`、xdist 実行時だけ有効）**
   - 各モジュールを1グループにする（モジュール共通の準備処理は1回）。
   - 重い5モジュールは数チャンクに分ける。
   - 合成データを使う4モジュールは1グループにまとめる。
   - 重いグループから先に投入する。
7. **不採用にした案**
   - MIN フラグの距離計算: 約10%速いだけで、レビュー済みコードを変える価値がない。
   - `translate` → `moved`: 速くならなかった。
   - `inspect_pairs` のメモ化: 証拠の連鎖17件の土台になっているため見送った。
   - xdist のワーカーごとに OCCT のスレッド数を制限する案と、最長グループを先に投入する案: 12・8・6並列のどれでも差が計測のばらつきの範囲だったため、取り消した。
   - `write_scene()` の高速化: 10.4秒の大半が C++ のメッシュ化（293部品、約50万頂点）。Python 側は約2.7秒。対象ファイルは証拠の写しとして保存されるため見送った。

## 4. 結果

| 段階 | 6並列の実時間 |
|---|---:|
| 変更前 | 334秒 |
| ＋STEP キャッシュ | 280秒 |
| ＋振り分けの改善 | 236秒 |
| ＋証明の効率化 | 149秒 |
| ＋`DistanceTo`・pivot の相対座標・`donor_parts` | 131〜134秒 |

並列数の比較（最終コード、719件合格）:

| 並列数 | 実時間 | 最小空きメモリ |
|---:|---:|---:|
| 6 | 131〜134秒 | 9.9 GB |
| 8 | 114秒 | 9.8 GB |
| 12（`-n auto`） | 109〜113秒 | 9.0 GB |

12並列はほぼ CPU の総量で頭打ちになる（ハイパースレッディング込みで実質7〜8コア相当）。README の推奨は `-n auto --dist loadgroup`。

## 5. レビュー指摘（未対応を含む）

1. **高: テストが git 管理外の `outputs/` を入力にしている**
   - 69モジュールのうち13モジュールが、`outputs/pg3-installable-candidate-r4/*.step`（各35 MB）などを読んでいる。
   - 新しく clone した環境ではテストが実行できない。conftest の「無視されている過去の生成物に依存しない」という方針にも反する。
   - 対応案: 入力を Git LFS で追跡する／生成用の fixture で作り直す／明示的なマーカーで区別し、分かりやすいエラーにする。どれにするかは要判断。
2. **中: 共有された形状でのメッシュ依存の測定**
   - `_source_rows()` はプロセス内で形状を共有している。`cq.Shape.BoundingBox()` はメッシュがあるとそれを使うので、他のテストが描画でメッシュを付けると値が変わる（前回のアンカーテストの実行順序依存はこれが原因）。
   - `camera_jig/id5_corner_vision.py` と `id5_corner_validate.py` は、パッドの境界箱を測定値として使っており、同じ危険がある。
   - `serviceability` と `assembly_contracts` の事前絞り込みは、境界箱が膨らむ方向なので安全側。
   - メッシュを付ける側の例: `simulation/pg3_scene.write_scene` は、`arm_assembly()` の中の `_source_rows()` の共有形状を `tessellate()` する。
   - 対応案: 測定には `scripts.assembly_io.bounds`（メッシュを使わない）を使う／共有前にコピーする。
3. **低: 運動学のガードがファイル全体をハッシュしている**
   - `verify_axial_motion_contract` は `gripper_design/pg3.py` 全体の SHA-256 を照合する。そのため import 行だけの変更でも23件が止まる。
   - 意図的に安全側へ倒した設計だが、レビュー済みの式を専用のモジュールに分ければ、保護の範囲を式だけに絞れる。ただし、その分離自体に再レビューが必要。
4. **情報: 証拠の連鎖と検査コードの変更**
   - 次の変更により、`outputs/` にある既存のチェックポイントを CLI で監査し直すには、作り直しが必要になる（意図された fail-closed 動作）。
     - `review_pg3_motion_clearance.py`（15の依存リスト）
     - `review_pg3_mechanism_insertion.py`（8）
     - `camera_jig/build.py`（4）
     - 前回の PR の `uv.lock`
   - テストはこの経路を通らない。
5. **情報: スレッドの過剰な割り当て**
   - `cq.Shape.distance` は OCCT のマルチスレッドを有効にしている。xdist の並列数を増やすとスレッドが過剰になりうる。
   - 競合がない状態では、マルチスレッドの方がシングルスレッドより1.37倍速い。
